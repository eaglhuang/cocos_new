# 團隊自動化代理分工計畫

Generated: 2026-06-04
Planning repo: 3KLife
Target framework: AI-Atomic-Framework / ATM
Status: planning source of truth

## 1. 目標與背景

ATM 目前已經有 Fast、Normal、Batch 三種治理通道，也有 task direction lock、batch checkpoint、evidence、pre-tool / pre-commit / CI 這些治理層。不過實戰中可以看到一個明顯問題：任務不是只有「改程式」一件事。AI 同時要讀文件、判斷 scope、寫程式、跑 validator、整理 evidence、處理 sandbox、最後 checkpoint / commit。這些工作全塞給同一個 agent，容易慢、容易漏、也容易偏移。

Team Agents 的目標是把一張任務卡變成一個小型施工現場：每個 agent 各司其職，但權限由 ATM 配置與檢查。它不是只服務 batch mode。Fast 小改、Normal 單張任務、Batch 多張任務都可以使用 team，只是 team 規模不同。

這份文件定義 ATM Team Agents 的規劃真相來源。它先作為設計文件，不直接修改 ATM framework source。後續若要實作，應從本文件拆出 `TASK-TEAM-*` 任務卡，並使用 ATM task-card-authoring 合約格式開卡。

### 大白話定位

- ATM 原本管「這次工作可不可以做、做完怎麼驗收」。
- Team Agents 管「這次工作中誰可以做哪一件事」。
- Team Agents 是加速層，不是放寬層。
- Team Agents 是治理合約，不綁定某一家 AI 編輯器或模型。

## 2. 核心設計原則

1. **Coordinator 唯一主控**
   - 只有 Coordinator 可以推進 ATM lifecycle。
   - 只有 Coordinator 可以 close / checkpoint / advance batch。
   - 只有 Coordinator 可以 git commit。

2. **寫入型權限是唯一裝備**
   - 同一組 active team 中，`git.write`、`task.lifecycle`、`file.write`、`database.write`、`pipeline.write`、`ci.write` 等寫入型權限同時只能給一個 agent。
   - 權限可以轉交，但必須經過 ATM lease/release 紀錄。

3. **讀取與驗證可以平行**
   - Reader、Scope Guardian、Validator、Evidence Collector 可以平行工作。
   - 但它們不能偽造 evidence，也不能把失敗 validator 包裝成 pass。

4. **語言 agent 可替換**
   - TypeScript 任務可使用 `implementer-typescript`。
   - Python 任務可使用 `implementer-python`。
   - C# / Cocos / data pipeline / DB migration 任務可以換成對應 agent。
   - 任務選用哪個 implementer 由 task metadata、repo probe、scopePaths、language hints 決定。

5. **Team 不取代 Fast / Normal / Batch**
   - Fast / Normal / Batch 決定任務治理通道。
   - Team 決定同一個治理通道內的角色分工。

6. **Team 不能繞過 ATM gate**
   - `allowedFiles`、evidence、validator、closure packet、batch checkpoint 仍然有效。
   - Team Agents 只協助更快完成這些要求。

7. **Review 簽章必須模型獨立**
   - Review Agent 不是同一個 AI 換一個提示詞人格；有效 reviewer 必須能提供與 Implementer 不同的 `modelCertificationId`、model/source identity 或供應來源證明。
   - 若無法證明 reviewer 與執行者是不同模型認證來源，該結果只能算 advisory note，不能算正式 review signature。
   - Review signature 是早期糾偏與 closure evidence，不取代 deterministic validator、Coordinator lifecycle 或 human review。

8. **沒有 subagent runtime 也要可用**
   - v1 可以先輸出 team checklist，由同一個 AI 依角色執行。
   - 未來有 subagent adapter 時，再真正 spawn read-only / validator / evidence helper。

9. **知識層是 advisory index，不是 registry**
   - `team-memory-shard` 可以被整理、索引、查詢，但不能成為第二真相來源。
   - 這一層只提供「開工前要注意什麼」的諮詢訊號，不直接取代 task card、evidence、closure packet、AtomicRegistry 或任何 promotion path。

10. **預設只有 Captain / Planner / Knowledge Scout 先查知識**
   - 正常流程下，不是每個 agent 都去掃整個知識庫。
   - Captain、Reader / Planner 或明確授權的 `Knowledge Scout` 先做 preflight query，再把命中的坑點濃縮進 brief 給 Implementer / Validator。

11. **檢索策略 lexical-first，vector optional**
   - 第一階段先靠 metadata filter + lexical / inverted-index search，優先追求快、便宜、可解釋。
   - 向量 rerank 只在 shard 數量夠大、lexical miss rate 明顯，且磁碟/延遲預算允許時才 opt-in。

12. **知識檔與 runtime cache 必須分層**
   - 可閱讀、可 review 的 canonical lesson shard 與機器生成的 index / embedding cache 不可混放。
   - framework 專屬 lesson 與 adopter / project 專屬 lesson 也要拆開，避免跨 repo 汙染。

13. **人類 / ADR gate 必須是 runtime 可見欄位**
   - Team Agents 不能只在文件裡說「高風險要找人」，而是要在 task / team runtime 中明確標示 `requiresHumanSignoff`、`requiresAdr`、`decisionClass`、`decisionReason`。
   - 若 gate 未滿足，狀態必須可進入 `blocked` / `escalated`，不能只留 warning。

14. **隊長自動決策只限低風險可回復事項**
   - Captain / Coordinator 可自動決定工作順序、子任務拆分、validator 排程、evidence 整理方式等低風險執行細節。
   - 但涉及資安、稽核、正式資料、權限模型、供應商選型、架構取捨、正式切換或政策降級時，不得自行放行。

15. **違規阻擋要覆蓋治理越權，不只檔案衝突**
   - Team runtime 除了 lease / fencing / path conflict，也要能阻擋 evidence 缺漏、reviewer independence 不成立、validator fail 被包裝成 pass、human / ADR gate 未滿足等情況。

## 3. 角色分工

| Role | 中文定位 | 可做 | 不可做 | 常見權限 |
|---|---|---|---|---|
| Coordinator | 工地主任 / 主控代理 | 決定流程、啟動 team、分派權限、checkpoint、commit、handoff | 不應直接大量改程式，除非沒有 implementer | `task.lifecycle`, `git.write`, `evidence.write` |
| Reader / Planner | 文件閱讀員 | 讀 task card、計畫書、source、整理摘要 | 不改 source、不關任務 | `file.read` |
| Knowledge Scout | 知識偵察員 / read-only sidecar | 查詢 lesson shard / knowledge index、回傳 top hits、整理 anti-pattern brief | 不改 source、不關 task、不自行升級成 gate | `file.read`, `knowledge.query` |
| Scope Guardian | 範圍守門員 | 檢查 allowedFiles、deliverables、scope amendment、跨 batch 衝突 | 不改 lock、不手改 `.atm/runtime` | `file.read` |
| Implementer | 實作者 | 依 allowedFiles 修改 source / docs / scripts | 不提交、不 checkpoint、不改 ATM runtime | `file.write` |
| Review Agent | 同儕審查員 / 獨立簽章 reviewer | 只讀檢查 Implementer 的 draft diff、atom spec、測試 evidence、scope drift、consumer contract、rollback 風險；輸出 early warning 或 review signature draft | 不改 source、不持有 `file.write`；不得與 Implementer 使用同一模型認證；不取代 Validator 或 Coordinator close | `file.read`, `review.signature.write` draft |
| Validator | 驗證員 | 跑 focused validators、typecheck、cache、回傳 command hash | 不把 fail 說成 pass | `exec.validator` |
| Evidence Collector | 證據整理員 | 整理 commandRuns、artifact paths、stdout/stderr hash、evidence draft | 不捏造 evidence、不關 task | `file.read`, optional `evidence.write` draft |
| Data Pipeline Agent | 資料管線員 | 產生資料管線 artifact、跑資料轉換 | 未授權不可寫正式資料 | `pipeline.write` |
| DB / Container Agent | DB/容器寫入員 | 寫 DB、容器、索引、外部狀態 | 未授權不可接觸外部資料庫 | `database.write` |
| CI Agent | CI 操作員 | 觸發 CI、讀 CI 結果、必要時更新 CI config | 未授權不可改 workflow | `ci.write` |
| Web Research Agent | 查詢員 | 查 web、下載文件、取得外部版本資訊 | query 與 download 權限分開 | `web.query`, `web.download` |

## 4. 權限裝備模型

Team permissions 分成兩種：

- `exclusive`：同一個 active team run 內只能有一個 owner。
- `shareable`：可多人使用，但仍可限制 scope。

### 權限目錄草案

| Permission | Mode | Scope | 預設 owner | 說明 |
|---|---|---|---|---|
| `task.lifecycle` | exclusive | task/batch | Coordinator | close/checkpoint/advance/release |
| `git.write` | exclusive | repo | Coordinator | stage/commit/tag/push 類寫入 |
| `file.read` | shareable | path/glob | Reader/Scope/Validator/Knowledge Scout | 讀文件與 source |
| `knowledge.query` | shareable | repo knowledge namespace | Reader / Knowledge Scout / Captain | 查 advisory knowledge index，回傳 top hits 與 anti-pattern |
| `file.write` | exclusive | path/glob | Implementer | 寫 source/docs/scripts/artifacts |
| `knowledge.index.write` | exclusive | repo knowledge runtime/cache | Coordinator | rebuild / compact / prune `.atm/runtime/knowledge/**` 生成物 |
| `web.query` | exclusive | domain/policy | Web Research Agent | 查詢網路資料 |
| `web.download` | exclusive | domain/path | Web Research Agent | 下載外部資料或套件 |
| `exec.validator` | shareable | command allowlist | Validator | 跑不改 source 的驗證命令 |
| `review.signature.write` | shareable | task/diff hash/review slot | Review Agent | 寫 review signature draft；正式 closure evidence 仍由 Coordinator / evidence gate 固化 |
| `exec.mutating` | exclusive | command allowlist | Coordinator 或專門 agent | 會改 repo/環境的指令 |
| `sandbox.write` | exclusive | environment config | Coordinator | 改 sandbox / temp root / 權限設定 |
| `pipeline.write` | exclusive | data pipeline path | Data Pipeline Agent | 寫資料管線輸出 |
| `database.write` | exclusive | DB/container target | DB Agent | 寫外部 DB、索引、容器 |
| `ci.write` | exclusive | CI provider/repo | CI Agent | 觸發或修改 CI |
| `evidence.write` | exclusive | task evidence | Coordinator | 寫正式 ATM evidence |

### 不可放寬規則

- `.atm/runtime/**` 不可由 team agent 手工編輯。
- `.atm/history/task-events/**` 不可手工編輯。
- `git.write` 不可給 Implementer。
- `task.lifecycle` 不可給非 Coordinator。
- `file.write` 必須是 task `targetWork.allowedFiles` 子集。
- `knowledge.index.write` 只能寫 knowledge runtime/cache，不能碰 `atomic-registry.json`、`.atm/history/**` 或 task 真相來源。
- `database.write`、`ci.write`、`web.download` 必須顯式授權，不可由預設 recipe 偷開。
- Review Agent 不可持有 `file.write`、`git.write` 或 `task.lifecycle`。
- 有效 Review Agent 必須記錄 reviewer model/source identity 與 `modelCertificationId`，且必須與本輪 Implementer 的模型認證不同；同一模型換 prompt、人格或 agent 名稱不算獨立 reviewer。
- review signature 不取代 validator pass；若 reviewer 與 Implementer 意見衝突，必須交由 Coordinator / Captain 或 human review 裁決。
- 若 task / runtime 標記 `requiresHumanSignoff` 或 `requiresAdr`，任何 agent 都不可把該 gate 視為 advisory。

## 6. Fast / Normal / Batch 使用方式

### 6.1 Fast

Fast 是小改入口，team 應該保持很薄。

建議 team：

- Coordinator
- Scope Guardian
- Validator

行為：

- 不預設啟動 Implementer subagent。
- `file.write` 通常由 Coordinator 持有。
- 只有當 task 命中大腳本、熱點路徑、或已知 recurring pitfall 時，Captain 才額外做一次 knowledge query。
- 超過 Fast 限制時升級 Normal。

### 6.2 Normal

Normal 是單張任務卡的標準施工現場。

建議 team：

- Coordinator
- Reader / Planner
- Knowledge Scout（可選）
- Scope Guardian
- Implementer
- Review Agent（可選；高風險 atom 或 repo 具備第二模型認證來源時建議啟用）
- Validator
- Evidence Collector

行為：

- Reader 先摘要任務合約。
- Reader / Knowledge Scout 可在開工前做一次 knowledge preflight，Captain 只把 top 3 坑點寫進 brief。
- Scope Guardian 先檢查 deliverables 是否都在 allowedFiles。
- Implementer 只改 allowedFiles。
- Review Agent 在 Implementer 完成 draft diff 後、正式 close 前做只讀審查；若發現 scope drift、missing tests、consumer contract 風險或 rollback 缺口，先回 early warning。
- Review Agent 必須與 Implementer 具有不同 `modelCertificationId` 或可驗證的不同模型來源；同一模型換 prompt / persona 只能留下 advisory note，不可算正式簽章。
- Validator 可平行跑 focused checks。
- Evidence Collector 整理 commandRuns draft。
- Coordinator 最後 close/commit。

### 6.3 Batch

Batch 是多張任務卡的佇列治理，不代表多個 Implementer 同時改同一份 source。

建議 team：

- Batch Coordinator
- Current-task mini team
- Read-only preview agents for next task

行為：

- 同一時間只有 current queue head 的 Implementer 可持有 `file.write`。
- 下一張卡的 Reader 可提前讀，但不可寫。
- Knowledge Scout 可替下一張卡預熱 query，但只回傳摘要，不得把整庫內容散播給所有 agent。
- Validator 可針對不衝突的靜態檢查預熱 cache。
- Evidence Collector 可整理草稿，但正式 evidence write 仍由 Coordinator 執行。

## 7. 安全規則

1. **Exclusive permission uniqueness**
   - 同一 teamRun 中，每個 exclusive permission 只能有一個 owner。

2. **No manual runtime edit**
   - 任何 agent 都不可手改 `.atm/runtime/**`。
   - scope amendment 必須走 CLI。

3. **Write scope must be bounded**
   - `file.write` lease 必須指定 paths。
   - paths 必須是 task `allowedFiles` 子集。

4. **Coordinator-only lifecycle**
   - close / checkpoint / advance / commit 只能由 Coordinator 執行。

5. **Explicit external side effects**
   - web download、DB write、CI write、pipeline write、sandbox write 都必須顯式授權。

6. **Evidence cannot lie**
   - exitCode 非 0 的 validator 不能被標成 validation pass。
   - 可記錄為 diagnostic evidence，但不能算通過。

7. **Adapter failure cannot bypass governance**
   - 真 subagent runtime 失敗時，只能退回 manual-team checklist。
   - 不可直接改成無治理寫入。

8. **Team Agents 採用併發契約，不定義併發 primitive**
   - Team Agents 負責「誰可以在 team runtime 中讀、寫、驗證、交接」。
   - CID E2 / `TASK-CID-0005` 負責定義底層 `Active Resource Index` / `Scope Lease Registry`、`leaseEpoch`、fencing token、wait-for graph 與 stale holder 規則。
   - Team Agents 只能消費這些狀態做顯示、診斷與 validator；不可把它擴張成第二套 task scheduler、第二套 Git，或新的 claim / close 決策來源。

9. **Reviewer independence required**
   - Review Agent 必須與本輪 Implementer 使用不同模型認證，至少要能比對 `modelCertificationId`、modelId/modelFamily、provider/source 或 runtime fingerprint。
   - 預設建議 cross-provider；若同 provider 但不同 certified model family，必須由 repo policy 明確允許。
   - 無法證明不同模型認證時，審查結果只能作 advisory warning，不可寫入正式 review signature。
   - Review Agent 不可寫 source，不可把自己升級成 Validator pass，也不可自行 close。

10. **治理越權必須阻擋**
   - 下列情況至少要進入 `blocked`、`needs-rework` 或 `escalated` 之一：scope violation、evidence missing、validator failed、reviewer independence missing、human sign-off missing、ADR missing、policy downgrade request。

## 8. ATM Team Agents 可組合治理落地介面

本章把 Team Agents 從概念推進到 ATM 可實作介面。重點是：Team 是可組合、可配置、可驗證的 runtime contract，而不是聊天提示。

### 8.1 Team CLI 草案

建議新增 `team` command group：

```shell
node atm.mjs team plan --task <id> --json
node atm.mjs team start --task <id> --recipe <recipe-id> --actor <id> --json
node atm.mjs team status --team <teamRunId> --compact --json
node atm.mjs team lease --team <teamRunId> --agent <agentId> --permission <permissionId> --json
node atm.mjs team release --team <teamRunId> --agent <agentId> --permission <permissionId> --json
node atm.mjs team complete --team <teamRunId> --json
node atm.mjs team abandon --team <teamRunId> --reason "<reason>" --json
```

v1 預設順序：

1. `team plan`：只讀 task 與 config，回建議 team，不寫 runtime。
2. `team start`：建立 `.atm/runtime/team-runs/<teamRunId>.json`。
3. `team status --compact`：只回目前 task、agents、leases、下一步命令。
4. `team complete`：由 Coordinator 在 close/checkpoint 前標記 team 完成。

建議任何 `team plan` / `team status` / `team validate` 都能額外輸出：

- `decisionClass`
- `decisionReason`
- `requiresHumanSignoff`
- `requiresAdr`
- `violationStatus`
- `escalationTarget`

### 8.2 `next --claim` 整合

`next --claim` 不應自動 spawn team，但應回傳 team 建議：

```json
{
  "teamRecommendation": {
    "enabled": true,
    "required": false,
    "recipeId": "atm.default.normal.typescript",
    "startCommand": "node atm.mjs team start --task TASK-AAO-0005 --recipe atm.default.normal.typescript --actor codex-main --json",
    "reason": "This task has multiple deliverables and validators; a scoped task team can reduce evidence and validation overhead."
  }
}
```

如果 task card 明確宣告：

```yaml
team:
  required: true
  recipe: atm.default.normal.typescript
```

則 `tasks close` / `batch checkpoint` 前必須確認 team run 已完成，否則回：

```text
ATM_TEAM_COMPLETION_REQUIRED
```

### 8.3 Permission Validation 錯誤碼

Team 啟動與 lease 變更時，ATM 必須檢查權限唯一性與範圍合法性。

併發資料來源採「只讀消費」原則：Team runtime 可以讀取 CID E2 定義的 `Active Resource Index` / `Scope Lease Registry` 來呈現 active holder、lease epoch、wait-for dependency 與 potential conflict；但 Team Agents 不得藉此建立新的任務排程、queue promotion、claim、close 或 commit 決策。這些生命週期仍由 ATM `next` / task close / batch checkpoint 與 Coordinator-only lifecycle 控制。

建議錯誤碼：

| Code | 觸發情境 | requiredCommand |
|---|---|---|
| `ATM_TEAM_PERMISSION_CONFLICT` | 兩個 agent 同時持有同一 exclusive permission | 修改 recipe 或 release 其中一個 lease |
| `ATM_TEAM_WRITE_SCOPE_EXCEEDED` | agent 要寫入不在 lease paths 的檔案 | `team lease` 或 `tasks scope --add` |
| `ATM_TEAM_REQUIRED_PERMISSION_MISSING` | recipe 缺 lifecycle/git/evidence 等必要 owner | 補 recipe permission |
| `ATM_TEAM_UNIQUE_OWNER_REQUIRED` | `git.write` / `task.lifecycle` 沒有唯一 owner | 指派 Coordinator |
| `ATM_TEAM_AGENT_PROFILE_MISSING` | recipe 指到不存在的 agent profile | 安裝或改用 fallback profile |
| `ATM_TEAM_RUNTIME_NOT_AVAILABLE` | 要求真 subagent，但目前 adapter 不支援 | 改用 manual-team checklist |

### 8.4 Hook / Gate 整合

pre-tool：

- 如果 active team 存在，寫入工具必須對應目前持有 `file.write` lease 的 agent。
- 寫入路徑超出 lease 時，回 `ATM_TEAM_WRITE_SCOPE_EXCEEDED`。
- web download / DB write / CI write / sandbox write 必須檢查對應 permission owner。

pre-commit：

- 只有持有 `git.write` 的 Coordinator 可以 commit。
- staged files 若屬於 active team，commit evidence 必須帶 `teamRunId`。
- 非 Coordinator commit 回 `ATM_TEAM_GIT_OWNER_REQUIRED`。

`tasks close` / `batch checkpoint`：

- 如果 task 要求 team，closure packet 必須包含 team summary。
- summary 至少包含：agents、permission leases、write scope、validators、evidence handoff、teamRunId。

### 8.5 Team Runtime Adapter

Team Agents 不應綁死某一家 AI 編輯器或模型。ATM 只定義 adapter contract：

```ts
interface TeamAgentRuntimeAdapter {
  id: string;
  supportsSpawn: boolean;
  supportsReadOnlyAgent: boolean;
  supportsWriteScopedAgent: boolean;
  spawnAgent(input: TeamAgentSpawnRequest): TeamAgentSpawnResult;
}
```

沒有 adapter 時：

- `team plan` 仍可輸出角色 checklist。
- Coordinator 可以手動依角色執行。
- evidence 記錄 `executionMode: "manual-team"`。

有 adapter 時：

- Reader / Validator / Evidence Collector 可以平行 spawn。
- Implementer 必須先取得唯一 `file.write` lease 才能 spawn。
- Adapter 失敗不能自動降級成無治理寫入。

### 8.9 Runtime 實作選型（純 API vs Claude Agent SDK）

Team Runtime Adapter 不一定要綁 Claude Code / Codex 這種編輯器形態。Adapter 是 contract，實作可以是純腳本：Node.js 或 Python 直接呼叫 Anthropic API，就能把 Reader、Validator、Evidence Collector、Knowledge Scout 這類角色生出來。本節定義「最省 token」與「需要 agent loop 才升級」的兩階段選型。

#### Tier A：純 API 呼叫（最節省）

定位：

- 直接打 `messages.create`，自己寫 tool_use ↔ tool_result 的小迴圈。
- 不載入 skill 清單、不掛 MCP server、不附編輯器的 system prompt。
- system prompt 完全自控；只塞「這個 agent 的職責 + 必要 context」。

適用角色：

- Reader / Planner：給一段文字、輸出摘要，通常一輪結束。
- Scope Guardian：讀 allowedFiles 與 diff，回 pass/fail + 理由。
- Knowledge Scout：對 lexical index 做 lookup，回 top hits。
- Validator wrapper：跑指令、回 exitCode + 摘要。
- Evidence Collector：把 commandRuns 整成 draft。

優點：

- 每輪 system prompt 通常 < 1 KB（vs Claude Code 動輒 30 KB+ skill / MCP 注入）。
- 可在 CI、cron、webhook 內跑，不需要 TUI。
- 模型認證 (`modelCertificationId`) 容易記錄——你直接知道呼叫了哪個 model id。
- 對 Review Agent 特別合適：要求「與 Implementer 不同模型認證」時，純 API 是最容易做到 cross-provider / cross-model-family 的方式。

侷限：

- 多輪 tool use、複雜 agent loop、權限提示、子代理 spawn 都要自己寫。
- 沒有現成的 skill / MCP 生態；要 MCP 能力得自己接 MCP client。

#### Tier B：Claude Agent SDK（不夠用時升級）

定位：

- 用 `@anthropic-ai/claude-agent-sdk`（Node）或 `claude-agent-sdk`（Python）。
- 仍是純腳本，沒有 TUI；但 agent loop、tool registry、permission mode、MCP 連線、子代理已封裝好。
- 可控制 `allowed_tools`、`disable_skills`、`disable_mcp` 來逼近 Tier A 的精簡度。

適用角色：

- Implementer：需要多輪 read → think → edit → run → fix。
- Coordinator：要管 lifecycle、串多個 agent、處理錯誤回滾。
- 真 subagent runtime adapter（M8 之後）：spawn read-only / validator / evidence helper。

優點：

- 不必自己重寫 agent loop 與 tool 協定。
- 內建權限模式（`acceptEdits` / `default` / `bypassPermissions`），便於對齊 ATM 的 lease 模型。
- 可掛 MCP，當任務需要外部能力（DB、CI、瀏覽器）時不必自造。

侷限：

- 預設會載入 skill 與 MCP context，token 比 Tier A 多。要省必須顯式設定 `tools` 白名單 + `disable_skills` + `disable_mcp`。
- 升級不是免費的：每多一層 SDK 抽象，debug 與決定論驗證就多一層成本。

#### 兩階段升級規則

1. 預設用 Tier A：能用純 API 一輪解決的角色，就不要升 SDK。
2. 出現以下訊號才升 Tier B：
   - 角色需要 ≥ 3 輪 tool use 且邏輯分支多。
   - 需要 permission mode、subagent spawn、MCP 工具。
   - 需要與 Claude Code / Codex 編輯器互通（共用 `.claude/agents/*`）。
3. 同一個 teamRun 內可混用：例如 Implementer 用 Tier B，Reader / Validator / Review Agent 用 Tier A。
4. 不可因為 Tier A 寫起來麻煩就硬升 Tier B；token 預算與 reviewer independence 是治理層的硬指標。

#### 「會不會變笨」的判斷

不會因為「跳過 skill / MCP context」而讓模型本身的推理能力下降——模型權重沒變、世界知識沒變、推理鏈長度沒變。會下降的只有：

- **任務相關 context 的取得便利度**：原本 skill 會自動提示「該用哪個工具」，純 API 下要靠你的 system prompt 明說。寫得清楚就沒差。
- **MCP 提供的外部能力**：如果該角色不需要那些能力，剝掉反而是訊號清理；只在角色真的需要 MCP 時才會「變笨」。
- **隱性 best-practice 注入**：skill 內有些寫死的流程提示。若這個 agent 的職責簡單明確（Reader、Validator 等），不需要那些提示。

實務經驗：

- Reader / Validator / Scope Guardian 從 Claude Code 改成純 API，品質幾乎無差，token 可省 90% 以上。
- Implementer 如果丟掉所有 skill，會明顯失去「先讀 CLAUDE.md → 跑 compute-gate → 上鎖」這類專案級流程提醒。這類 agent 該留在 Tier B，或在 system prompt 內手動把專案規矩塞進去。
- Review Agent 用純 API 反而**更好**：強制 reviewer 不繼承 Implementer 的 skill / MCP 視角，獨立性更乾淨，符合 §7.9 reviewer independence。

#### 對 ATM 的落地建議

- `atm.teamRecipe.v1` 應允許 agent 宣告 `runtimeTier: "raw-api" | "agent-sdk" | "editor"`。
- `atm.teamRun.v1` 應記錄每個 agent 實際走的 tier 與 `modelCertificationId`，作為 closure evidence。
- M4 (`team plan`) 的輸出應建議每個角色的 tier，預設保守：Reader / Validator / Knowledge Scout / Review Agent 預設 Tier A，Implementer / Coordinator 預設 Tier B。
- 後續可開 `TASK-TEAM-00xx`：「Team Agents runtime tier contract」與「Raw-API adapter reference implementation」。

#### 供應商中立原則（Vendor Neutrality）

ATM 是開放、中立的治理框架，因此 Tier A / Tier B / Tier Editor 的具體實作**不得綁死任何單一供應商**。前述 Anthropic API、`@anthropic-ai/claude-agent-sdk`、Claude Code 只是「目前最完整、首批落地的參考實作」，不是唯一選項。架構上必須讓採用者自由指定或自接其他廠商方案。

中立邊界的硬規則：

1. **ATM core 只認 contract，不認 vendor**
   - `atm.teamRecipe.v1` / `atm.teamRun.v1` / `TeamAgentRuntimeAdapter` 不得出現 `anthropic` / `openai` / `google` 等供應商專屬欄位作為必要欄位。
   - 供應商資訊一律透過 `runtimeProvider`、`modelCertificationId`、`adapterId` 這類抽象欄位記錄，內容由 adapter 自行填。

2. **每個 Tier 都需要可替換的 adapter 介面**
   - Tier A（raw-api）：定義 `RawChatAdapter`，contract 為「給 messages + tools，回 assistant content + tool_use」；任何符合 OpenAI-compatible / Anthropic / Gemini / Bedrock / Azure / local Ollama 的 endpoint 都可包成 adapter。
   - Tier B（agent-sdk）：定義 `AgentLoopAdapter`，contract 為「給 prompt + tool registry + permission policy，回事件流」；可包 Claude Agent SDK、OpenAI Assistants / Responses API、LangGraph、Google ADK、Vercel AI SDK、自家 loop 等。
   - Tier Editor：定義 `EditorAgentAdapter`，可接 Claude Code、Codex、Cursor、Continue、Aider、Cline 等。

3. **採用者可在三個層級指定供應商**
   - 全域預設：`atm.config.json` 內 `runtimeProviders.default`。
   - Recipe 級：`atm.teamRecipe.v1` 內每個 agent 可宣告 `runtimeProvider`（例如 Implementer 用 Anthropic Sonnet、Review Agent 強制用 OpenAI GPT 以滿足 reviewer independence）。
   - Task 級：task card frontmatter 可覆寫，但必須通過 policy 檢查（例如不可降級到無認證來源）。

4. **Reviewer independence 與多供應商天然契合**
   - §7.9 要求 Review Agent 與 Implementer 模型認證不同；最乾淨的滿足方式就是跨供應商。
   - ATM 應提供 `reviewerIndependencePolicy`，可宣告 `"different-provider"` / `"different-model-family"` / `"different-certification"` 三種強度。
   - 採用者可自由組合：Anthropic + OpenAI、Anthropic + Gemini、Anthropic + 本地 Llama 等。

5. **內建三大廠商 adapter，預設可用、可切換、可移除**
   - ATM 安裝後預設**內建**三家供應商 adapter，讓新採用者開箱即用、不必先煩惱選哪一家：
     - `@atm/adapter-anthropic`（Claude 系列：Opus / Sonnet / Haiku）
     - `@atm/adapter-openai`（GPT 系列：GPT-5 / GPT-4o / o-series）
     - `@atm/adapter-microsoft`（Azure OpenAI + Azure AI Foundry，涵蓋 Azure 部署的 GPT、Phi、其他 Foundry 模型）
   - 內建意義等同 ATM 預裝的 integration skill：與 core 一起發布、`atm doctor` 會檢查、文件首頁有對應範例；但**不強制使用**——採用者可只配置其中一家的 API key，其他 adapter 雖在磁碟上但不會被啟動。
   - **預設供應商**：建議設為 `anthropic`（Claude Sonnet 4.6 / Opus 4.7），理由：(a) ATM 的治理語彙、Tool Use 協定、Agent SDK 文件最完整；(b) M2 的「90 分鐘第一張卡」承諾在 Anthropic adapter 上已驗證；(c) 與 Claude Code editor tier 一致，便於跨 tier 比對。採用者可在 `atm.config.json` 一行切換為 `openai` 或 `microsoft`。
   - **可選性下載 / 移除**：每個內建 adapter 都是獨立 package + lazy import，採用者可：
     - `npx atm adapter disable openai` → 停用但保留檔案。
     - `npx atm adapter remove microsoft` → 真正從 node_modules 移除以縮小體積。
     - `npx atm adapter enable <id>` → 重新啟用。
   - **變肥的代價是有意接受的**：以三家 SDK 合計 ~20-30 MB node_modules 換取「git clone 後立即可跑」的進入門檻，比讓新採用者先研究 adapter 選型更有價值。CI / 容器場景若需精簡，再用 remove 命令處理。
   - **不在內建清單內的供應商**（Gemini / Bedrock / Ollama / 本地 Llama / 企業 gateway）仍透過 §6 BYOA 機制接入，地位等同社群 plugin，不會被 ATM core 視為二等公民。
   - **內建不等於耦合**：三家 adapter 仍實作同一組 `RawChatAdapter` / `AgentLoopAdapter` SPI，ATM core 對它們的呼叫方式與對 BYOA adapter 完全相同；任何時候都能整組換掉而不需 patch core。

6. **採用者可自接（Bring-Your-Own-Adapter, BYOA）**
   - 公開 adapter SPI（service provider interface），任何第三方都能實作並註冊。
   - 註冊機制：`atm.config.json` 的 `runtimeProviders.custom` 區段，指向採用者本地或私有的 adapter package。
   - 自家 inference cluster、企業內部 gateway、社群微調模型都能被當成一等公民接入，不需 patch ATM core。

7. **Closure evidence 必須記錄實際使用的供應商**
   - 每個 agent 的 evidence draft 必須包含 `runtimeProvider`、`modelId`、`modelCertificationId`、`adapterId`、`adapterVersion`。
   - 這讓 audit、reviewer independence 驗證、未來 incident retro 都可追溯到具體供應商與版本。

8. **預設參考實作不等於唯一實作**
   - ATM 可以「附帶」Anthropic adapter 作為開箱即用範例，但 docs 必須明確標示這是 reference adapter；同等地位的還有 OpenAI / Gemini / Ollama 等。
   - 任何文件、CLI help、error message 不得使用「ATM 需要 Claude」「ATM 基於 Anthropic」這類措辭；只能說「ATM 預設提供 Anthropic adapter，您也可以選擇其他供應商或自接」。

對 task card 的影響：

- `TASK-TEAM-00xx`（runtime tier contract）必須同時定義 `RawChatAdapter` / `AgentLoopAdapter` / `EditorAgentAdapter` 三組 SPI，且至少提供兩個非同供應商的 reference adapter 才算 done，避免「contract 看起來中立、實作只有一家」的隱性綁定。
- 後續可再開 `TASK-TEAM-00xx`：「Multi-provider adapter registry」與「Reviewer cross-provider policy enforcement」。

### 8.6 組合與替換策略

Team recipe 應允許用參數替換 agent：

```json
{
  "replace": {
    "implementer": "implementer-python"
  },
  "when": {
    "language": "python"
  }
}
```

替換規則：

- replacement agent 必須滿足原 role 的必要 permission。
- replacement agent 不可額外拿未授權 exclusive permission。
- 若 replacement 需要新增權限，例如 `pipeline.write`，task card 必須顯式宣告。
- fallback 可以降級成 generic implementer，但不能自動取得更寬 file scope。

### 8.7 Rollout 順序

實作時不要一次把 subagent、hook、runtime 全塞進去。建議漸進：

1. Schema + docs。
2. `team plan` dry-run。
3. `team start/status` runtime。
4. Permission lease validator。
5. Hook / pre-commit enforcement。
6. `next --claim` playbook integration。
7. closure packet team summary。
8. 真 subagent runtime adapter。

這個順序的好處是：前四步就能改善 AI 操作清晰度；最後一步才碰最複雜的多代理執行。

### 8.8 Team Knowledge Index（advisory-only）

本子系統的目標不是建立第二套 registry，而是讓 `team-memory-shard` 可以被 Captain / Planner / Knowledge Scout 快速查詢，從「上次踩過的坑」提煉成這輪 brief。

核心分層：

- canonical shard（可 review / 可 commit）：`.atm/knowledge/framework/shards/**` 或 `.atm/knowledge/project/shards/**`
- generated index / cache（可重建 / 可刪除）：`.atm/runtime/knowledge/**`
- framework 專屬 lesson 只留在 ATM framework repo；project / adopter 專屬 lesson 只留在被治理 repo

CLI 草案：

```shell
node atm.mjs team knowledge build --scope project --json
node atm.mjs team knowledge query --task <id> --top 5 --json
node atm.mjs team knowledge stats --json
node atm.mjs team knowledge compact --dry-run --json
```

查詢流程：

1. 先用 `repo / channel / domain / path prefix / atom / validator` 做 metadata filter。
2. 再用 lexical / inverted-index shortlist，預設只取 top 5。
3. 只有在啟用 opt-in 模式、且 lexical 命中品質不足時，才做 vector rerank。
4. Captain 只把精簡後的命中摘要寫進 `team-brief.md`，不把整個知識庫全文丟給每位 agent。

性能與磁碟守則：

- 一 shard 一 lesson；soft cap 4 KB、hard cap 16 KB，超過就拆 shard 或先摘要。
- runtime lexical index 預設總量上限 10 MB / repo。
- embedding cache 預設關閉；若啟用，只能放在 `.atm/runtime/knowledge/embeddings/`，且預設上限 50 MB、可由 compact / prune 清掉。
- full rebuild 只用於 repair；平時應以 hash / mtime 做 incremental build。

治理邊界：

- knowledge index 是 advisory source，不得成為 task truth、closure authority、AtomicRegistry promotion path 或自動升版來源。
- `knowledge.index.write` 只能更新 `.atm/runtime/knowledge/**` 生成物，不能碰 `.atm/history/**`、`atomic-registry.json`、task ledger。
- `team-memory-shard` 可以間接提供 upgrade 線索，但正式 `behavior.evolve` 仍只走 proposal + evidence + review。

sidecar 落地補充：

- 目前 `tasks import` 匯入後的 canonical task JSON 主要保留 lifecycle / scope / validator / repo 邊界，尚未保留 `dispatch_pattern`、`phase_0`、`phase_1`、`condition_review` 這類 sidecar 派工欄位。
- 因此在 `TASK-TEAM-0020+` 這條知識軌上，sidecar 的 dispatch source 仍以 Markdown task card 為準，ATM ledger JSON 只負責 task identity、dependency、status、validator 與 claim/close lifecycle。
- 這個缺口現在由 `TASK-TEAM-0025` 承接：把 dispatch metadata preservation 納入 `tasks import` / canonical schema；在它落地前，Captain 仍應明確要求 sidecar 同時讀 task card 與 ledger。
- `TASK-TEAM-0026`：TEAM safe mirror/import ledger reconciliation lane（可先做 Phase 0 planning opener；Phase 1 target_repo 仍是 AI-Atomic-Framework）。
## 9. 里程碑

任務卡開卡順序改以里程碑為準，不再沿用早期草稿的 M1-M8 編號。每個里程碑都要先帶來可感的任務卡效果，再往 runtime 自動化推進。

### M0：Planning Roster Reset

目標：

- 重建 `TASK-TEAM-*` 任務卡為 ATM 標準格式。
- 建立 team-agents task index。
- 不改 ATM framework source。

建議任務：

- `TASK-TEAM-0001`：team agents planning roster reset。

### M1：Minimum Useful Task Crew

目標：

- 每張任務卡都有最小可用小隊。
- `Atomization Planner` 成為每張卡必備角色。

目標：

適用情境評估：

| 情境 | 目前適配度 | Team Agents 邊界 |
|---|---:|---|
| A. 單一人類本機使用多個 AI 工具 | 8.5 / 10 | 最適合；Team Agents 可把 sidecar 讀取、validator、evidence 彙整變成明確 runtime contract。 |
| B. 多個人類各自電腦開發同一 repo | 6 / 10 | 可作治理規範與回報格式；真正跨機 lease 仍需 Git / PR / CI / 遠端 lease service 補強。 |
| C. 多 Agent 在同一 server / agent framework 跑同一 repo | 5 / 10 現況，E2 後可到 8 / 10 | 長期潛力高，但現況不能共用同一 working tree 任意寫；需 E2 resource index、fencing、deadlock detection、worktree/patch isolation。 |

- `TASK-CID-0012`：Team Agents brokered write integration contract（CID-side planning bridge；Team Agents 後續 implementation card 必須由 Team Captain 另行開立）。

Brokered write 對 Team Agents 的分工邊界：

- Coordinator 仍是唯一 `task.lifecycle` / `git.write` / `evidence.write` owner。
- Scope Guardian 檢查 allowedFiles、dirty tree、active lease、broker lane。
- Atomization Planner 提供 atom_id、atom_cid、shared generator / projection / validator / artifact surface。
- Implementer 在 Direct Brokered Lane 仍可自己寫；若同檔 CID disjoint 衝突升級，Implementer 只能交 `PatchProposal.v1`。
- Neutral Write Steward 是獨立寫入合併角色，只能拿 scoped `file.write`，不可拿 `git.write` 或 `task.lifecycle`。
- Validator / Check Runner 驗證 final patch；Review Agent 寫 review signature draft，不變成 Write Steward。
- Lead Writer 只作 break-glass，不是 normal / batch recipe 的預設角色。
- Write Broker 是 repo/workspace 層級的跨任務服務，不是每個 teamRun 私有的 helper；每張任務可以有自己的 Team Agents，但所有 active teamRuns 都必須向同一個 Broker registry 註冊 write intent，否則無法偵測跨任務衝突。
- Broker 本身不應是 AI Writer。它是 deterministic registry / conflict calculator；真正動態產生的是 Neutral Write Steward / Write Agent。

## 11. 後續實作驗收方向

文件階段：

- 文件存在於 `docs/ai_atomic_framework/team-agents/`。
- Markdown 無亂碼。
- 權限表包含 git / file / web / exec / sandbox / pipeline / database / CI。
- 權限表包含 `review.signature.write`，且明確標示 Review Agent 只能寫 review signature draft。
- 知識層文件明確區分 canonical shard 與 generated cache。
- 每個 exclusive permission 都有唯一 owner 規則。
- Milestone 可直接轉成任務卡。

實作階段：

- 同一 recipe 兩個 agent 拿 `git.write` 必須 fail。
- `file.write` 指向 `.atm/runtime/**` 必須 fail。
- Normal task 可建立 team plan。
- Batch current task 可建立 per-task team。
- 非 Coordinator commit 必須被 hook 擋下。
- 無 subagent runtime 時仍能輸出可操作 team checklist。
- Captain knowledge preflight 只回 top hits，不要求每個 agent 讀完整 shard corpus。
- runtime index / embedding cache 可被重建與 compact，預算超標時會有明確 warning 或 fail。
- framework lesson 與 project lesson 查詢時會正確分層，不互相污染。
- vector rerank 關閉時，系統仍能用 lexical-only 正常工作。
- Review Agent 若缺少 `modelCertificationId` / model source identity，或與 Implementer 的模型認證相同，審查只能算 advisory note，不能算正式 review signature。
- review signature disagreement 會進入 Coordinator / Captain / human review，而不是自動覆蓋 validator 或 task lifecycle。

## 12. Assumptions

- 本文件先作為 3KLife planning repo 的規劃真相來源。
- 本步不直接修改 ATM framework source。
- 後續正式開卡時使用 `TASK-TEAM-*` 系列。
- Team Agents 是可選加速層，不取代 Fast / Normal / Batch。
- Coordinator 是唯一 lifecycle / git owner，這條不允許被 adopter recipe 放寬。
- 真 subagent runtime 是 M8 之後的能力；M1-M7 先把治理模型做穩。
- knowledge index 不是 registry，不可成為第二 authority、第二 task store、第二 promotion path。
- canonical shard 與 generated cache 分層：前者可 review / 可 commit，後者可重建 / 可刪除。
- 預設 lexical-first；vector 只作 opt-in rerank，不是 v1 必備依賴。
- framework 知識與 adopter / project 知識分 repo 存放；跨 repo 共享靠 query policy，不靠硬塞進同一個目錄。
- Review Agent 只有在可驗證不同模型認證時才算正式簽章者；否則仍可提供建議，但不能被計入 quorum。

### M2 完成後的「90 分鐘第一張卡」承諾

M2 收口後，ATM 對新採用者要兌現一個可量化的承諾：**從 git clone 到第一張卡 close 並產生 closure-packet + patrol-report，總時間不超過 90 分鐘**。這個承諾的存在理由是補上 7-Agent Factory 在「明確時長 + 開箱即用範例」這兩件事上對 ATM 仍有的優勢；M2 把所有必要範本與 validator 落地後，這條時間線就有了客觀可驗證的底盤。

承諾的時間切片：

| 分鐘區間 | 採用者實際看到的事 | 由哪張卡兌現 |
|---|---|---|
| 0-15 | `npx create-atm my-app --agent claude-code` 完成；`node atm.mjs doctor --json` 全綠 | 既有 |
| 15-30 | 複製 `examples/team-agents-minimal/team-brief.md`，改 4 個 allowedFiles 欄位、改 task 標題 | TASK-TEAM-0004 |
| 30-60 | `node atm.mjs next --prompt "..."` → Agent claim → 改 1 個小檔 → `npm run typecheck` 綠 | 既有 + TASK-TEAM-0002/0003 |
| 60-80 | `node --strip-types scripts/validate-team-agents-templates.ts` 綠；agent-report.md 寫好 | TASK-TEAM-0004/0005 |
| 80-90 | `node atm.mjs tasks close --json` → closure packet 寫入；產出第一份 patrol-report.md | TASK-TEAM-0006 + 既有 closure pipeline |

驗收這個承諾的方式：M2 三張卡全部 done 後，至少做一次 wall-clock dry run，由 M2 收口前未接觸過 ATM 的觀察者執行，全程未超過 90 分鐘即為通過。dry run 結果寫進 `examples/team-agents-minimal/QUICK_START_WALK_THROUGH.md`。

- 範例值（task id, allowedFiles, owner）使用 `EXAMPLE-` 前綴或註解標示「請改成你自己的」。
- 不引入 `.atm/` runtime 檔——範例不模擬實際 ATM state，只示範文件流。
- 範例值不可被 `validate-neutrality-scanner.ts` 標為 protected-surface 違規。
- 採用者複製整個目錄到自己的 repo 後，應該不需要再讀計畫書即可動手。

這個範例目錄是 ATM 對「Factory 開箱即用儀式感」的回應：你不必懂 27 個 packages 與 9 個警察家族，只要懂 6 個範本檔加 4 個欄位的 task 卡，就能跑完第一條治理鏈並看到證據包。

### 團隊等級 L1~L5(正式定義,2026-07-11)

`--team-size` 除 `small | medium | large` 外,正式支援五級團隊等級 `L1~L5`。五級是「三種 teamSize + 兩層治理增援」的疊加,不是第四、第五種 roster 尺寸:

| 等級 | teamSize 對映 | 班底定義 | 適用情境 |
|---|---|---|---|
| L1 | small | 小卡班底:`Task Captain`、`Atomization Planner`、`Code Builder`、`Check Runner`(四治理角色,不可移除) | 1-2 核心檔、低風險 |
| L2 | medium | L1 + `Reader / Planner`、`Evidence Curator`(`Knowledge Scout` 可選) | 3-5 檔、有 validators/evidence |
| L3 | large | L2 + `Scope Sentinel`、`Task Lieutenant` 協調邊界 | 跨多核心檔、>600 行大腳本、涉 closure/git-head |
| L4 | large | L3 + 獨立 `Review Agent`(reviewer independence 生效,建議跨 provider) | 高風險 atom、需要獨立簽章 |
| L5 | large | L4 + per-role provider 指定(多廠商混編)、`QA Lead`、`Closure Steward` 全席 | 付費 dogfood、論文級多廠商協作演示 |

規則:

- 自動 sizing(`decideTeamSizing`)只產出 small/medium/large(即 L1~L3);L4、L5 只能由人工 `--team-size L4|L5` 或 task card 顯式宣告啟用,並在 captain decision 記錄 `source: manual`。
- L4/L5 的 `teamSize` 欄位維持 `large`,追加語意記錄在 `teamLevel` 欄位,並於 roster 與 provider 選擇層生效;不得只改字面等級而不啟用對應角色。
- L4 若無法滿足 reviewer independence(無第二模型認證來源),必須降回 L3 並留下 rationale,不得掛名 L4。
- 本表是 L1~L5 的唯一定義來源;其他文件(含 CLI spec、正典表)引用本節,不得另行定義。

### 隊長與副隊長原則

- 隊長是唯一決策中心。
- 副隊長只在複雜任務、跨 phase 任務、或需要多小隊並行時出現。
- 如果一張任務卡開始出現「先做哪一塊、誰先讀、誰先驗證、誰先整理 evidence」這類高協調成本問題，通常就該加副隊長。

## 15. Agent 名冊與職責

### `Task Captain`

職責：

- 決定小隊大小。
- 決定是否需要副隊長。
- 決定任務是否可以進入實作。
- 決定是否 close-ready。

禁區：

- 不可繞過 ATM gate。
- 不可讓隊員超出 allowedFiles。
- 不可用口頭結論代替 evidence。

### `Task Lieutenant`

職責：

- 任務太複雜時協助隊長拆 phase。
- 追 blocker。
- 協助整理跨 agent 依賴。

### `Atomization Planner`

職責：

- 每張任務卡開工前先做 atom/map 化規劃。
- 判斷 primary atom、related atoms、capability touched、command surface。
- 檢查是否需要更新 path-to-atom-map。
- 檢查是否有大腳本風險，是否該先拆小。

禁區：

- 不直接改 source。
- 不自行 claim / close。
- 不替 Implementer 做 code change。

### `Scope Sentinel`

職責：

- 檢查 allowedFiles。
- 檢查 dirty tree。
- 檢查 claim overlap。
- 檢查是否需要拆 task。

### `Code Builder`

職責：

- 依派工單實作。
- 只碰被授權的檔案。
- 做完回報，不自行 close / commit。

### `Review Agent`

職責：

- 只讀檢查 `Code Builder` / Implementer 產出的 draft diff、atom spec、測試 evidence、scope、consumer contract 與 rollback 風險。
- 在 final closure 前提出 early warning，讓 Implementer 可以及早修正 drift、missing tests 或合約落差。
- 產出 review signature draft，包含 verdict、阻塞理由、advisory 建議、reviewed diff hash 與引用 evidence。

任命資格：

- 必須記錄 `reviewerAgentId`、`reviewerModel`、`reviewerProvider/source`、`modelCertificationId`、`reviewedAuthorAgentId`、`reviewedAuthorModel`、`reviewedDiffHash` 與 timestamp。
- 必須能證明 reviewer 與本輪 Implementer 具有不同模型認證；同一模型換 prompt、persona、agent 名稱或上下文視角，不算有效 Review Agent。
- 預設建議跨 provider；若同 provider 但不同 certified model family，必須由 repo policy 明確允許並留下 rationale。

禁區：

- 不直接改 source。
- 不持有 `file.write`、`git.write` 或 `task.lifecycle`。
- 不把 review signature 當成 validator pass。
- 不在模型認證無法獨立時被計入 quorum。

### `QA Lead` 與 `Check Runner`

職責：

- 決定要驗什麼。
- 跑 validators。
- 把 pass / fail / diagnostic 分清楚。

### `Evidence Curator`

職責：

- 整理 command-backed evidence。
- 收 commandRuns、artifact、hash、validator 摘要。
- 幫隊長快速做 closure packet。

### `Knowledge Scout`

職責：

- 查詢 repo-local lesson shard / knowledge index。
- 依 `path / atom / validator / domain / channel` 回傳 top hits。
- 只把 compact 摘要交給隊長或 Planner，不把整庫全文散播給每位 agent。

禁區：

- 不直接改 source。
- 不可把 advisory hit 宣告成強制 gate。
- 不可自行把 memory shard 升級成 task truth、evidence 或 registry 記錄。

### `Closure Steward`

職責：

- 結案前檢查 closure packet、ledger、events、git-head。
- 確認是否可安全 close。

### `Atomic Police Agents`

職責：

- 固定巡邏。
- 盤查規則。
- 輸出摘要報告。
- 不直接改 source。

可用角色：

- `Scope Police`
- `Evidence Police`
- `Ledger Police`
- `Atom Map Police`
- `Encoding Police`
- `Runner Sync Police`

## 17. 隊長決策模型與任務卡重排原則

### 隊長決策模型

- 隊長必須在派 `Code Builder` 前先取得 `Atomization Planner` 結論。
- 若啟用 knowledge layer，預設由 Captain / Reader / Knowledge Scout 先查，Implementer 只收摘要版 top hits。
- 碰到 `tasks.ts`、`next.ts`、`evidence.ts`、`hook.ts` 這類大腳本時，原子規劃師不可省略。
- 超過 2 個核心檔、跨 repo、涉及 git / evidence / closure、或大於 600 行腳本時，建議加入副隊長。
- `map update needed: yes` 時，隊長要先確認 task allowedFiles 是否包含 atom map。
- `task split needed: yes` 時，先停 coding，回報人類或開新卡。
- 隊長不可繞過 ATM gate，不可讓隊員超出 allowedFiles，不可用口頭 pass 代替 evidence。
- 隊長不可因為 knowledge hit 很像就直接當成事實；命中內容仍要以當前 task、當前 source 與 validator 驗證為準。

### 任務卡重排原則

- 任務卡的開卡順序應以里程碑為準，不以舊的編號順序為準。
- 如果既有 task 卡順序和里程碑順序不一致，優先重排，不要硬沿用錯誤順序。
- 如果一張卡的內容已偏離當前里程碑，重開新卡通常比沿用舊卡安全。
- 建議開卡順序：
  - 先開 M0 文件與名冊卡
  - 再開 M1 最小小隊卡
  - 再開 M2 回報格式卡
  - 然後才進 M3-M6 的 runtime、lease、巡邏擴充

## 18. Atomic Police Agents 巡邏隊

### 定位

- 原子警察是固定巡邏型 agent。
- 預設 read-only，只巡檢、報告、建議，不直接改 source。
- Review Agent 與 Atomic Police 不同：Review Agent 是任務內針對 Implementer 產物做 peer review 與簽章，且必須具備不同模型認證；Atomic Police 是固定節奏或特定 gate 前的巡邏隊，重點是盤查治理狀態與提出風險報告。

### 常見巡邏時機

- 每日中午巡邏
- 任務 claim 前巡邏
- 任務 close 前巡邏
- batch checkpoint 前巡邏
- 大腳本改動前巡邏

### 常見巡邏隊

- `Daily Noon Patrol`
- `Close Gate Patrol`
- `Big Script Patrol`
- `Multi-Agent Collision Patrol`
- `Ledger Consistency Patrol`
- `Runner Sync Patrol`

### 巡邏報告

- 巡邏結果輸出成 `patrol-report.md`。
- 報告要能讓人類一眼看懂哪裡有風險、要不要繼續、下一步該做什麼。
- 巡邏隊如果發現風險，應該建議任務卡，而不是偷偷改 source。

### 巡邏隊能帶來的效果

- 提前抓出 scope 衝突。
- 提前抓出 evidence 不完整。
- 提前抓出 ledger / events 不一致。
- 提前抓出大腳本風險與 atom map 缺口。
- 讓人類知道自動巡邏真的做了什麼。

## 19. Broker-owned Write Actor 邊界

### 問題

- 當 CID 判定為 same-file but CID-disjoint，ATM 已經有 broker / steward lane。
- 目前 Team Agents 的權限模型仍以 `Coordinator` 持有 `task.lifecycle`、`git.write`、`evidence.write` 為主。
- 如果後續真的把 Neutral Write Steward / Write Agent 做成可執行 runtime actor，需要先講清楚它到底是「Coordinator 的一個受控角色」，還是「只聽 broker 指令的獨立角色」。

### 規劃結論

- 可以存在 **broker-owned write actor**，而且它應該是獨立於一般 Implementer / Review Agent 的專用角色。
- 但它**不應該**成為第二個 lifecycle owner，也不應該自己擁有 commit / close 權限。
- 比較正確的切法是：
- `Broker / steward lane` 決定「是否需要中立寫手」與「它可寫哪些 scoped files」。
- `Broker-owned write actor` 只消費 proposal / merge plan / steward plan，產生 final scoped patch 與 write evidence。
- `Coordinator / Captain` 仍保留 `git.write`、`task.lifecycle`、`evidence.write`，負責 commit、close、release、handoff。

### Authority chain

- `Coordinator` 是單一 Team 的 local owner；負責 team 內節奏與正式 task lifecycle。
- `Broker` 是跨 Team 的 conflict governor；負責 same-file、CID、shared-surface、steward merge 與 historical-delivery 的上位裁決。
- 因此兩者不是平行雙頭；當問題進入 broker 管轄域時，`Coordinator` 應聽 `Broker`。
- 但 `Broker` 也不接管一般 team-local 日常節奏；沒有衝突域事件時，`Coordinator` 仍保有自主權。

### 為何不讓它完全脫離 Coordinator

- 如果 Write Actor 同時能自己 commit / close，ATM 會重新出現第二套調度中心。
- 那會讓 Team runtime 與 broker runtime 同時持有收口權，形成真正的多頭馬車。
- 真正要避免的不是「Write Actor 聽 broker」，而是「Write Actor 同時又是 lifecycle owner」。

### 建議權責切面

- `Broker-owned write actor`
  - 可有：`file.write`（限 broker/steward 已核准 scope）
  - 可有：讀 proposal / merge plan / scope lock / write evidence output
  - 不可有：`git.write`
  - 不可有：`task.lifecycle`
  - 不可有：`evidence.write` 最終收口權
- `Coordinator / Captain`
  - 保留：claim / start / stop / close / reconcile / release
  - 保留：delivery commit / historical reconcile / final evidence routing
  - 負責：是否啟動 broker-owned write actor，以及寫完後是否接受結果

### 衝突處理規則

- 若 `Coordinator` 想直接推進 claim / commit / close，但 `Broker` verdict 已判定 `needs-steward`、`blocked-cid-conflict`、`blocked-shared-surface` 或需要 historical delivery，則 `Coordinator` 必須停下並改走 broker 指定路徑。
- 若 `Broker` 路徑超出 task card scope、acceptance 或 closure authority，`Coordinator` 不可自行忽略，而是升級給 `Captain / human` 裁決。
- 正式規則可總結為：
  - `Broker verdict overrides Coordinator decisions within broker-governed conflict domains.`
  - `Outside broker-governed conflict domains, Coordinator retains team-local lifecycle authority.`

### 後續實作方向

- 應新增一條明確 runtime contract：
  - broker 可 materialize 一個只擁有 scoped `file.write` 的 Write Actor
  - 該 actor 只接收 broker-approved input，不直接接收一般 task 自由指令
  - actor 完成後只回傳 write evidence / final patch 結果，由 coordinator 決定是否進入 commit / close
- 這樣可以把「寫檔執行」從 coordinator 手上拆開，但不把 governance 收口權拆散。
